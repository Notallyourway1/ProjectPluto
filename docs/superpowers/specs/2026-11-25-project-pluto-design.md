# Project Pluto for KSP: design

Date: 2026-11-25
Status: draft, awaiting approval

## Intent

A standalone KSP 1.12.x mod that adds the Project Pluto / SLAM nuclear ramjet cruise missile as one
part, built the same way as the user's Project Sundial mod (generated model, part config, C# plugin,
`build-mono.sh`). The user wants to recreate the mission from the "What if Project Pluto had flown?"
video in their own game: boost off a ramp, cruise on a nuclear ramjet with no fuel, dive low, and
toss 16 hydrogen bombs that each leave a mushroom cloud.

## Goals

1. **One part on the pad.** The missile, its three solid boosters, its reactor-powered ramjet and its
   16 warheads are all one part. No other part is needed except a launch clamp or ramp if the player
   wants one.
2. **Integrated boosters that drop off by themselves.** On staging, the boosters fire. When their fuel
   runs out the plugin hides the booster shells, throws them off as visual debris, removes their
   mass and drag, and hands over to the ramjet.
3. **Nuclear ramjet that burns only air.** Unlimited range in the atmosphere, no thrust at low speed,
   peak performance around Mach 3–4, cuts out above the atmosphere.
4. **Reactor plugin with real Tory figures:** warm-up, temperature readout, SCRAM, an unshielded
   radiation zone that doses kerbals the missile flies over, and a breach if it crashes hot.
5. **Manual flight until the bombing run, then a built-in autopilot** that dives, terrain-follows at
   150 m and releases the warheads, so the low-level run is playable.
6. **16 warheads tossed one at a time** from hatches on top. Each detonates on impact with a
   1-megaton version of the Sundial effect (fireball, mushroom cloud, shock front, part damage).
7. **Real history in the text.** Part description and README use the researched specs, say where
   sources differ, and say what is invented for gameplay.

## Non-goals (v1)

- Sonic boom damage or effect.
- Boosters or warheads as real KSP vessels (they are plugin-driven visuals/projectiles).
- Fission fragments in the exhaust, terrain blocking radiation.
- KSP 2. Career balance beyond a sensible tech node and cost.

## Anti-goals

- Requiring any other mod (including Sundial) or any DLC.
- Breaking Sundial when both are installed: no shared type names, no shared GameData paths.
- Frame-rate collapse from several clouds at once.
- Presenting invented numbers as historical.

## Constraints and environment

- KSP 1.12.5 at `<KSP folder>`, installed through CKAN, with
  Kopernicus, Scatterer, EVE, Waterfall and others. The mod must not depend on any of them.
- Build: Mono `mcs` (present at `/opt/homebrew/bin/mcs`) against the KSP `Managed` folder, same as
  Sundial's `build-mono.sh`. Target .NET Framework 4.7.2-compatible C#.
- Model: generated by a Python script with Pillow (11.3.0 installed) and taniwha's `io_object_mu`
  `mu.py`, which is **not on this machine** and must be downloaded from
  https://github.com/taniwha/io_object_mu with the user's permission.
- No automated test harness exists for KSP; verification is a compile plus an in-game test checklist.

## Approaches considered

- **A. Engine in config only.** Air-only engine and intake in the part config, no code. Stable and
  quick but no reactor behaviour, no auto-jettison, no warheads.
- **B. Config engine plus reactor plugin (chosen by the user).** Same engine, plus a C# plugin for the
  reactor, booster jettison and warheads. Follows the Sundial pattern.
- **C. Fully custom engine in code.** Rejected: fights KSP's aero and thrust handling for no visible gain.

Warhead effect options were: scaled Sundial effect (**chosen**), simple explosion, inert test shapes.
Boosters: separate part was proposed; the user chose **integrated boosters with auto-detach**.

## Design

### Mod layout

```
ProjectPluto/                      source project (in the repository root)
  Source/*.cs                      namespace ProjectPluto
  Source/BuildPluto.py             model + texture generator
  build-mono.sh, build.sh, ProjectPluto.csproj, README.md
  GameData/ProjectPluto/
    Parts/Pluto.cfg
    Parts/Assets/PlutoExterior.mu, PlutoSkin.png
    Plugins/ProjectPluto.dll
```

Part name `projectPlutoSLAM`. Category Engine (it is primarily a propulsion part), tag words
`pluto slam nuclear ramjet missile tory`. Tech node `nuclearPropulsion`. Cost about 45,000 funds
(builder's call).

### Model (BuildPluto.py)

Built with the same lathe approach as `BuildCasing.py`, at real size:

- Body: 26.8 m long, 1.5 m diameter, ogive nose, slight boat-tail at the nozzle.
- Gold-coloured forward section (roughly the first third), steel-grey elsewhere, hatch outlines on top
  (16, in a row), "PLUTO" / "SLAM" markings in the texture.
- Three small canards near the nose, three fixed tail fins at the back.
- Ventral scoop intake under the forward body.
- Three booster casings around the tail, each its own transform (`Booster1`..`Booster3`) with its own
  collider and its own thrust transform (`boostThrust`), so the plugin can hide them.
- Ramjet nozzle thrust transform `ramjetThrust`; warhead release point transform `warheadHatch`.
- Nodes: bottom stack node and surface attach (to sit on a ramp or launch clamp).

### Engines

Two `ModuleEnginesFX` on the part:

- `engineID = Boost`: SolidFuel, thrust through `boostThrust`, not throttleable, staged. Tuning target:
  from a 30–45° launch with full warheads, burnout at Mach 2 or more and at least 3 km altitude.
  Starting point: about 1,500 kN total for about 20 s (builder tunes).
- `engineID = Ramjet`: propellant **IntakeAir only**, thrust through `ramjetThrust`, not staged,
  started by the plugin. `velCurve` near zero below Mach 1, rising to a peak at Mach 3–4, falling off
  past Mach 5. `atmCurve` cuts out as the air thins. Reference thrust 170 kN (Tory II-C). Tuning
  target: level flight reaches about Mach 3 at 150 m and about Mach 4 at 9 km on Kerbin.
- `ModuleResourceIntake` on the part for the built-in scoop.

Ramjet throttle sets reactor power demand; the engine's thrust limit follows actual reactor power.

### Plugin modules

**ModulePlutoBoosters**
- Watches the Boost engine. When its SolidFuel is empty (flameout) and boosters are still on: hide the
  three booster transforms and disable their colliders, spawn three visual debris copies with an
  outward and backward push that fall under gravity and are removed on ground contact or after 60 s,
  switch to a clean drag cube (the part provides `Boosted` and `Clean` drag cubes via
  `IMultipleDragCube`), and tell the reactor to start.
- `IPartMassModifier` removes booster dry mass after jettison. A "Jettison boosters" event and action
  group exist as a manual override.
- Persists `boostersJettisoned`, so a loaded save shows the clean missile.

**ModulePlutoReactor**
- States: Cold → Warming → Running → Scrammed, plus Breached.
- Warm-up about 20 s of game time from start to full power. Right-click readout: state, power (MW, up
  to 600), core temperature (°C, up to about 1,277 at full power), airflow.
- Without enough airflow (too slow, or above the atmosphere) the core temperature climbs; past a limit
  it SCRAMs automatically. A manual "SCRAM reactor" event and action group exist, plus "Restart reactor".
- **Radiation:** while power is above zero, every loaded kerbal (in a part or on EVA) on the same body
  gets dose rate `k × (power / 600 MW) / r²`, with `k` chosen so a Mach 3 pass at 150 m overhead
  gives about 0.28 Sv (the video's figure). From the pass integral `D = kπ / (h·v)`, `k` is about
  13,600 Sv·m²/s. Doses accumulate per kerbal in a `ScenarioModule` and persist. Messages appear at
  0.1 Sv and 1 Sv. At 6 Sv (config value) the kerbal dies.
- **Breach:** if the part is destroyed while the reactor is above a power threshold, spawn a small
  dust/steam plume and leave a stationary radiation source at that spot, at 10% strength for 10
  minutes of game time.

**ModulePlutoWarheads**
- `warheadCount = 16` (config). Each warhead's mass (about 0.5 t) is removed when it is released
  (`IPartMassModifier`).
- "Release warhead" event and action group. Optional toggle: "Auto-release every N s" (config default
  60 s, matching the video's one-per-minute spacing).
- A released warhead is a plugin-owned projectile (a small mesh, not a vessel), thrown up and backward
  from `warheadHatch` with the missile's velocity plus a toss, then flown ballistically with gravity
  and simple drag. Its position is held relative to the celestial body in double precision so floating
  origin shifts and Krakensbane do not move it. It detonates on contact with terrain or water, or
  after a 120 s safety timer.
- Detonation: a scaled copy of Sundial's effect plus damage to loaded parts within the damage radius,
  with the same chaining rule (another Pluto part in range is destroyed with its own effect).

**Detonation effect (copied from Sundial)**
- Copy the Sundial effect classes into the Pluto namespace with Pluto names (`PlutoDetonationEffect`
  etc.). No shared type names with Sundial.
- Refactor the hard-coded distances in the effect (cloud top 11,000 m, early cloud top, cap radius,
  shock range, and so on) into one size scale passed to `Spawn`.
- 1 Mt defaults: fireball radius about 280 m, cloud top about 3 km, damage radius about 500 m
  (all config values, builder may tune for looks).
- Fewer puffs per burst than Sundial (about a third) so two or three clouds at once stay smooth.
  With one warhead per minute and a ~100 s effect, no more than two should overlap normally.

### Control and lift (Claude's call)

- The part is its own command part: uncrewed probe core (`ModuleCommand`, needs a little
  ElectricCharge, which the reactor supplies while running and a small battery covers before), SAS,
  and a modest reaction wheel.
- Steering: the three canards are animated control surfaces (`ModuleControlSurface`, one per canard
  transform: `Canard1`..`Canard3`), plus a few degrees of gimbal on the ramjet nozzle.
- Lift: the body counts as a lifting body (`ModuleLiftingSurface` on the part, small area) so it can
  hold level flight at Mach 3 and 150 m at a few degrees of angle of attack. Tuning target added:
  level flight at 150 m / Mach 3 needs no more than about 5° angle of attack.

### Reactor timing (Claude's call)

The reactor starts warming up when the boosters ignite and reaches full power by about booster
burnout, so the ramjet takes over with no gap in thrust. Historically the reactor was only switched
on at cruise altitude far from people; the README says so. Radiation scales with power, so the
launch site gets a brief, low dose.

### Blasts hitting a Pluto (Claude's call)

- A warhead's blast damages parts in range like Sundial's. A Pluto missile in range is destroyed and
  its reactor breaches (plume plus lingering source). Its remaining warheads do **not** go off:
  real thermonuclear weapons do not detonate from a nearby blast, and it keeps cloud counts low.
- Warheads still in the air are not chain-detonated.
- The releasing missile is normally about 11 km away by the time its warhead lands, far outside the
  damage radius; if it is inside, it is damaged like anything else.

### Persistence (Claude's call)

Saved: booster jettison, warheads remaining, auto-release setting, reactor state and temperature,
kerbal doses and active breach sources (ScenarioModule, with body, position and expiry time).
Not saved: warheads in flight and clouds in progress; they are dropped on a scene change or reload.

### Radiation reach (Claude's call)

Only kerbals in loaded vessels and on EVA (physics range, about 2.3 km) are dosed. That covers any low
pass; kerbals in unloaded vessels are not. The README says so.

### Autopilot (user asked for it; details are Claude's call)

**The player has manual control for the whole flight until they commence the bombing run** (user's
request, 2026-11-26). There are no cruise or general autopilot modes: launch, climb, cruise and the
approach are flown by hand (SAS still works).

**ModulePlutoAutopilot** flies the missile only during the bombing run, through `vessel.OnFlyByWire`,
with PID loops for pitch (via a target flight-path angle), roll (bank to turn) and throttle (speed).
Right-click menu: **Commence bombing run** (also an action group), **Abort bombing run**, run height
(default 150 m, minimum 100 m), run speed (default Mach 3), and the "Release on target" toggle.

The bombing run:
- **Dive:** from wherever the player engages it, the missile descends at a limited pitch and g-load to
  the run height above the ground and settles at the run speed.
- **Terrain follow:** holds the run height above the ground. It samples terrain height ahead along
  the flight path (every ~250 m out to ~5 km, using the body's terrain height lookup, not raycasts,
  so it works beyond loaded terrain) and climbs early for ridges, limiting pitch and g-load. Over
  water it holds height above sea level.
- **Release:** warheads release either on the auto-release timer (the video's line of strikes) or,
  with "Release on target" on, at the computed toss point so the warhead lands on the target, using
  the same ballistic model as the warhead projectile.
- **End:** when the warheads are gone, or on Abort, control returns to the player in level flight.

Target: the vessel's selected target (any vessel, including a planted flag), or the active navigation
waypoint if one is set. No target: the run holds the current heading.

Safety: any manual pitch, yaw or roll input during the run aborts it and hands control back, with a
screen message. If the reactor SCRAMs or the vessel leaves the atmosphere, the run aborts.

Tuning targets: in terrain follow at Mach 3, height stays within about 100–250 m above ground over
Kerbin's highlands, with no ground strikes on a flight across the highlands west of KSC; turns to a
target at no more than about 6 g.

### Text

Part description and README in Sundial's style: what Pluto was, the real numbers, the disagreements,
and a clear list of what is invented (booster count, warm-up time, radiation formula, warhead toss,
1 Mt effect sizes, kerbal dose threshold). Sources listed with links.

## Verification

- Compile with `build-mono.sh` against the local KSP `Managed` folder, no warnings treated as ignorable
  if they point at real problems.
- In-game checklist (needs the user, or computer use with their OK): part appears and looks right in the
  VAB; launch from a ramp; boosters burn and drop at burnout; ramjet takes over and holds about Mach 3
  at 150 m; reactor readouts, SCRAM and restart work; a kerbal on the ground under a low pass gets
  about 0.28 Sv; 16 warheads release and each produces a cloud; frame rate stays playable; save and
  reload mid-flight keeps state; Sundial and Pluto installed together both still work; nothing
  takes control before "Commence bombing run"; the run dives to 150 m, holds height across the
  highlands, flies to a planted flag, drops a warhead on it with "Release on target", aborts on
  manual input, and hands back control when the warheads are gone.
